# 업데이트와 LED 권한

0.2.0까지의 빌드는 ad hoc 서명으로, 코드 내용이 바뀌면 코드 식별 조건(DR)의 cdhash도 바뀐다. 입력 모니터링에 예전 앱을 허용했더라도 새 코드와 일치하지 않아 권한 오류가 발생할 수 있다. [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)

0.2.1부터 `standalone/build.sh`는 `scripts/sign-app.py`를 호출한다. 빌드 Mac에서 무료 로컬 코드 서명 인증서를 한 번 만들고 이후 빌드에서 재사용한다. DR은 bundle ID와 해당 인증서에 연결되며 전역 인증서 신뢰 설정이나 TCC 데이터베이스를 수정하지 않는다. 다른 인증서로 서명한 앱은 같은 bundle ID를 써도 이 DR을 충족하지 못한다.

최초 서명 전환 시에는 입력 모니터링에서 기존 항목을 제거하고 새 앱을 추가하는 작업이 한 번 필요할 수 있다. 이후에도 같은 인증서·bundle ID·설치 위치를 유지해야 한다. 앱이 사용자 대신 개인정보 권한을 승인할 수는 없으며, 실제 OS 업데이트·다른 Mac에서 권한이 유지되는지는 별도 검증 대상이다.

빌드 인증서와 개인 키가 든 전용 키체인은 `~/Library/Application Support/Clipboard AI Solver Signing`에 보관한다. 이 폴더는 빌드 머신에서만 사용하며 앱·DMG에는 넣지 않는다. 폴더 전체를 비공개로 백업하고 삭제하거나 매 빌드마다 재생성하지 않는다. 개인 키의 임시 PEM/P12는 등록 후 제거하며 저장된 키는 내보내기 불가로 등록한다. 키체인 잠금 해제 비밀번호 파일은 사용자 전용 0600, 폴더는 0700이다.

기존 서명 정보가 일부 사라지거나 인증서가 만료되면 빌드를 중단한다. ad hoc 서명이나 다른 인증서로 자동 대체하지 않는다. 서명 폴더 전체가 사라지면 새 인증서가 생성되므로 권한 재허용이 다시 필요하다. 30년 유효한 로컬 인증서를 사용하며, 빌드 머신 이전 시에는 동일한 서명 폴더를 복원해야 한다.

이 자체 서명은 Apple Developer ID나 공증을 대신하지 않으며, 내려받은 사용자의 최초 실행 허용 절차는 그대로 필요하다. Apple이 권장하는 일반 공개 배포 방식은 Developer ID 서명·공증이다. [Apple 코드 서명 안내](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html)

검사:

```bash
python3 -B Tests/SigningCheck.py
```

임시 인증서·키체인·앱 사본만 사용해 내용이 달라진 두 빌드의 DR 유지, 다른 인증서 배제, 불완전한 서명 정보 보존을 검증한다. 실제 입력 모니터링 권한 승인이나 물리 LED 작동을 검증하는 테스트는 아니다.

2026-10-20 검증: 서명 검사 2개(손상된 JSON 하위 사례 포함), 기존 기능 전체 검사, 설치 교체·원복 4개, 임시 앱 직접 실행·정상 종료 통과. 앱 Swift 소스 19개는 모두 원본 해시와 일치한다. 독립 리뷰 승인 및 손상된 JSON 오류 처리 지적 반영. 최종 `/Applications` 앱과 0.2.2 DMG의 동일한 서명 번들·SHA-256·개인 서명 파일 미포함 확인.

실제 권한 유지 검증: 사용자가 0.2.1의 새 서명에 최초 권한을 허용한 뒤 ‘3회 깜빡임 확인’이라고 응답했다. 같은 인증서로 0.2.2를 빌드하고 cdhash는 변경되었지만 DR과 이전 서명 조건은 유지됨을 검사했다. 입력 모니터링 설정을 변경하지 않고 `/Applications` 앱을 0.2.2로 교체·실행한 뒤, 사용자가 ‘재등록 없이 3회 깜빡임’이라고 확인했다. 따라서 이 Mac의 해당 업데이트에서는 실제 LED 권한 유지까지 검증했다. 다른 Mac·OS 버전이나 인증서 변경 이후까지 검증한 것은 아니다.
